# 工作流引擎、Skill 与案例：实际价值和易用性分析

日期：2026-09-23  
本轮范围：分析与方案对比，不实施代码改造。用户已明确允许评估重新设计写法，不要求严格兼容旧定义。本文中的新字段均为设计草案，不能交给当前引擎运行。

## 1. 摘要

aiwf 有实际价值，但目前使用方需要理解过多引擎内部规则。核心收益是长任务可恢复、人工检查点、产物契约、过程追踪和批量实例管理；不应把“每件事都拆成节点、每次推进都调 CLI”本身当成价值。

建议选择“小型结构化工作流 + 一致的数据引用 + 面向当前任务的执行协议”。让引擎承担类型、作用域、重复实例和确定性推进，让 Agent 负责创作、工具执行、业务判断及向人收集信息。

优先级：先消除语义不一致，再简化常用写法，最后重写 Skill 和案例。仅换成 YAML、增加示例或缩短字段名，不能解决根因。

### 2.2 已确认的使用问题

| 问题 | 当前事实 / 位置 | 对使用方的影响 |
|---|---|---|
| 数据引用会变成文本 | `engine.py:130 render` 总是把字符串模板替换成字符串；`_begin_instance` 用它处理子流程 inputs | `${item}` 从对象变成 JSON 字符串，`${item.number}` 从数字变成字符串；子流程 Schema 可能直接拒绝 |
| 相似引用在不同位置能力不同 | `resolve_condition_value` 使用点路径解析；`_resolve_items:579` 却直接查 `ctx[key]` | `when` 中 `plan.chapter_count` 可用，items 中 `plan.chapters` 不可用 |
| 条件引用未统一进入依赖图 | `references_check` 会读取 `when`，`dependency_graph:297` 未收集它 | 校验认得某项依赖，修订传播却遗漏这条依赖；依赖可复用时可能沿用旧分支决策 |
| 全局可变键掩盖来源和轮次 | task 输出写 `context[output_key]`；老案例 `chapter_revise` 覆盖 `chapter_draft` | 看变量名无法区分初稿、修订稿、上一章；重做与进入下一轮容易混淆 |
| 模板既承担文字拼接又承担依赖声明 | 依赖主要从 prompt 的 `${...}` 和 consumes 提取 | prompt 改写会影响修订范围；自然语言提到文件并不一定形成依赖 |
| 简单工作流也有结束陷阱 | Skill 最小示例只有一个 task；结构校验允许；`_advance:1835` 在无后继时失败 | “最小示例校验通过”不等于“能完成运行” |
| 内联循环暴露内部图结构 | 自动补 start/end，但路由目标验证只认手写 body 节点 | 作者可能被迫增加“定稿”task，只为给成功路由一个出口；实际定稿校验有业务价值时才应保留 |
| Agent 需要维护调度栈 | run-workflow 文档要求从父 run 找 child run，再切过去；start/end/确定性 branch 仍要 complete | 无业务产出的机械调用多，嵌套后更容易上报错对象 |
| 自动质检缺乏反馈契约 | 案例要求 branch 只输出 PASS/REVISE | 下一次修订知道“不合格”，却拿不到结构化的不合格原因，可能重复猜测 |

只读探针输出摘要：

```text
render({"chapter":"${item}","number":"${item.number}"}, item={"number":1})
  -> chapter 为 '{"number": 1}' 字符串，number 为 "1" 字符串

when: {"eq":[{"var":"plan.chapter_count"},3]}
  -> True

items: {"var":"plan.chapters"}
  -> KeyError: items variable 'plan.chapters' not found in context

仅由 when 消费 plan 的 gate：
  dependency_graph()["gate"] -> 空集合
  stale_closure({"plan"}) -> 空集合

单 task 工作流：
  validate_workflow -> 通过
  successors("draft") -> []
```

以上是具体行为验证，不是完整集成测试。分支修订的最终影响还取决于实际拓扑及其他依赖。

### 2.3 案例与 Skill 的具体评价

**老小说案例**：13 个节点、9 条显式 edges。每轮章节细纲先列目录统计 N，再写 N+1 章；结束判断再次列目录。这把实例身份交给 Agent 和文件名推断。目录中有旧运行文件、草稿或不连续章号时，容易得出错误结论。文件存在也不代表已验收完成。

**三章仿真案例**：已使用 foreach，但多处仍让 Agent 读完整章节清单，再按 index 找当前章，未充分利用已注入的 item。`gate.when` 当前为 `{"eq":[1,1]}`，所以“完整跑通”不能证明三章完备性检查有效。该结论针对留存案例，不否定 foreach 已有能力。

**Skill**：主入口 63 行，创建参考 416 行，执行参考 186 行。渐进披露方向正确，但创建者仍需一次掌握大量规则和例外。尤其完整示例中的 `"chapter":"${item}"` 与子流程 `chapter: object` 契约不匹配：模板字符串化后会失败。这类冲突应靠实现和可执行示例消除，不能继续靠警示文字叠加。

旧报告中“模板不支持点路径”“错误信封不含 error”等内容已有实现修复，不应重复列为现存问题。

## 3. 什么场景值得使用 aiwf

| 场景 | 最有价值的边界 | 不值得过度固化的部分 |
|---|---|---|
| 小说 | 大纲验收、章节身份、局部返工、连续性材料、产物交接 | 每段创作动作都成节点；让模型数目录或反复报空结果 |
| 短剧 | 分集/分镜实例、剧本与素材关联、版本与验收 | 工作流里编码具体剪辑工具的全部操作 |
| 游戏开发 | 按资产清单重复处理、验证点、可定位的失败实例 | 每次编辑器点击和每个文件改动 |
| 软件开发 | 需求确认、实现阶段、测试证据、评审和交付门槛 | 预先画死每次调试路径、每个函数改动 |

任务拆分原则：一个节点至少提供一种收益——可独立验收、可独立重试、可复用产物或可独立交接。否则应考虑合并进相邻任务。

一次性、短小、不需要恢复或验收的任务，直接使用 Skill 往往更划算。长任务或重复运行流程才更能抵消定义和协议成本。

需要区分两种可靠性：引擎证明“某步骤按协议完成并有证据”；它不能仅凭 Agent 上报的 PASS、字数或 exit code 就证明业务产物质量。严格门槛应要求对应工具结果或人工结论。

## 4. 三条路线的比较

| 路线 | 内容 | 收益 | 代价 / 局限 | 建议 |
|---|---|---|---|---| 
| A. 整理现有写法 | 统一默认值，修复引用缺陷，更新模板和文档 | 改动小、短期收益明显 | 作者仍需思考图、context、exports 和驱动栈 | 作为基础修复 |
| B. 小型结构化写法 | 常用流程表达成顺序、批量、有限返工、验收；输入和产物显式声明 | 可读、可校验，保留恢复和追踪价值 | 需定义作用域、结束语义和迁移边界 | 推荐主方向 |
| C. 自然语言自由流程 | 只写阶段目标，Agent 自行决定下一步和状态映射 | 文件最短、探索最自由 | 更依赖 Agent；恢复、依赖和一致性更难保证 | 适合 task 内部，不宜替代整个引擎 |

推荐 A 修复语义底座，B 改善常用表达；C 留在任务内部。不要同时维护数套等价变量语法或构建通用脚本语言。

JSON 仍可作为唯一存储格式。YAML 只改善标点与长文本书写，不改善数据类型、作用域、循环身份；暂不作为优先工作。

## 5. 建议的简化方式

### 5.1 数据引用、文字插值各做一件事

保留 `${...}` 用于 prompt 或路径里的文字插值；引入一种统一的结构化引用表示，例如 `{"ref":"..."}`，在 inputs、items、条件操作数等数据位置返回原始类型。ref 这个拼写只是候选，不必为了新增它而保留多套等价写法。

现在：

```json
{
  "inputs": { "chapter": "${item}" },
  "items": { "var": "plan.chapters" }
}
```

候选：

```json
{
  "inputs": { "chapter": { "ref": "item" } },
  "items": { "ref": "plan.chapters" }
}
```

语义要求：

- 对象仍是对象，数字仍是数字，文件引用仍是文件引用。
- 所有位置共享一套路径解析和引用收集，不能各自实现一半。
- 文件引用默认只表示文件，不默默读取正文；items 可按明确契约读取 JSON 清单。
- 必需输入缺失应指出“哪个步骤、哪个输入、期望哪个来源”，不静默变成空串。
- 数据引用的数量未必减少，但需要记住的规则必须减少。

### 5.2 把“使用哪些材料”从 prompt 提出来

可考虑把 task 的材料声明统一为 use / inputs（实施时二选一，不同时堆叠）。最简单的同名引用可以用列表；需要别名时才写映射。

候选：

```json
{
  "id": "draft",
  "use": ["outline", "characters", "item"],
  "prompt": "根据本章规划创作正文，保持人物动机与世界规则一致。",
  "output": { "file": "novel/chapters/${item.number}.md" }
}
```

执行 Agent 获取的任务包应同时列出材料名称、解析后的值或路径、预期产物与反馈。这样它不用从自然语言中猜出哪些字符串是文件，也不用在每个 prompt 重复“先读文件、最后只输出 $file”。

依赖从 use / inputs 声明产生；prompt 插值仍可补充依赖。consumes glob 作为特殊场景扩展，不必成为入门必学概念。

产物声明不代替 Agent 写文件。引擎可验证路径存在、协议 JSON 的结构；正文质量仍由工具、Agent 或人判断。文件内容不自动塞进 prompt。

不建议无条件把全部父 context 注入子流程，也不建议统一使用“上一节点输出”：分支、跳过和重做后，“上一节点”含义不稳定。可省写同名材料，但来源仍需明确且可追踪。

### 5.3 循环按用途分开

| 业务意图 | 适合的结构 | 身份 / 结束条件 |
|---|---|---|
| 已有章节、分镜或资产清单 | foreach | 引擎分配实例，清单全部处理结束 |
| 同一产物反复改到合格 | 有上限的检查返工 | 保持同一产物与实例身份，记录 attempt 和修改原因 |
| 写作过程中才决定下一章 | 动态 foreach 或以后单独设计 repeat-until | 新条目由 Agent 决定；引擎记录实例；必须显式完结 |

前两种应当是简洁的常用路径。动态创作先利用现有 manifest 机制，不为统一外观立刻增加另一套循环状态机。

引擎维护的是通用实例索引、尝试次数和状态；“下一章写什么、故事是否完结”属于业务判断，仍由 Agent 负责。这不违背纯状态机约束。

返工必须提供明确的失败原因，并设置本地尝试上限。达到上限后交给人决定或明确失败，不能自动当作合格。

### 5.4 小说章节块的候选表达

以下只展示已有大纲之后的章节块，不是完整可运行定义。假设 `plan.chapters` 为章节数组或声明过的 JSON 清单引用，`plan.outline` 为大纲产物；字段名称尚未锁定。

```json
{
  "id": "chapters",
  "type": "foreach",
  "items": { "ref": "plan.chapters" },
  "inputs": {
    "outline": { "ref": "plan.outline" }
  },
  "nodes": [
    {
      "id": "draft",
      "type": "task",
      "use": ["outline", "item"],
      "prompt": "按本章规划写正文，覆盖关键事件，保持人物和设定一致。",
      "output": {
        "file": "novel/chapters/${item.number}.md"
      },
      "check": {
        "criteria": ["关键事件完整", "冲突有推进", "章尾有钩子"],
        "max_attempts": 3
      },
      "review": {
        "requirements": ["本章是否可以定稿"]
      }
    }
  ],
  "result": { "ref": "draft" }
}
```

期待的效果：没有目录计数、手写回边、空完成节点，也无需为循环结束额外造一个没有业务工作的 task。检查仍然是可审计的 Agent 动作，人工验收仍要等人，不能因为内嵌字段而被引擎“自动批准”。

边界：这个块本身没有表达跨章节连续性。若实际创作需要前章摘要或设定状态，应声明为材料并由顺序实例间传递，不能假设子流程自动知道兄弟产物。示例变短不代表业务依赖可以省略。

这里的 output、check、result、use 都是候选能力，当前 schema 不支持。是否新增 check，还是先由模板生成“质检 task + branch”，应根据维护成本比较；不要求一步做完。

### 5.5 分支先收敛常用模式

- 普通顺序：按声明顺序前进，最后一步自然结束。
- 批量：每个实例完成后由引擎切换到下一实例。
- 确定性判断：引擎自己求值并推进，保留决策审计，无需 Agent 发空 complete。
- 主观质检：Agent 返回结论及原因；引擎决定返工或前进。
- 人工验收：明确的暂停点，用户给结论后才推进。
- 复杂多路业务分支：保留显式路由能力，但作为高级用法。

常见的“通过就继续、拒绝就重做当前任务”不应需要解释 null、default 和隐藏 end 的差异。自动推进也必须受步数保护，并在任务、人工输入、人工验收、等待条目或失败处停下。

### 5.6 执行协议隐藏内部调度

目标：Agent 每次只需知道“现在做什么、用什么材料、把结果报给哪个动作”。

建议根 run 提供当前可执行叶子任务，内部保留 child run 用于审计。任务包带明确目标和动作标识，上报时核对，防止恢复或重做后把旧结果写给新动作。人不需要来回阅读父子 run，Agent 也不需要自己维护栈。

这是执行体验建议，不要求把所有已有 CLI 合并成一个万能命令。查看状态应尽量保持只读；自动推进和对账放在哪个明确的状态变更入口，需要在后续协议设计中锁定。

### 5.7 Skill 与案例重新分层

主入口继续渐进披露，但从“命令与类型手册”转为“选择最小流程模式”：

1. 先判断是否需要工作流；是否有恢复、复用、验收或批量价值。
2. 入门只展示顺序、材料、产物、人工验收。
3. 按需加载批量、质检返工，再进入动态条目与复杂路由。
4. 执行指南围绕任务包与反馈，不要求执行者先读创建指南。
5. 审计、修订和失败恢复保留独立参考。

示例体系应展示同一场景逐渐增加需求：最小开篇 → 逐章创作 → 单章返工 → 人工验收 → 动态章节。每个例子都必须能结束，且有一个负向路径，不能只展示最终 completed。

仿真策略调整：隔离的 Agent 只读 Skill；换 Agent 接管时不读取作者解释；既检查产出，也检查失败路径与实际执行的约束。人工审批的模拟仅用于测试，必须标识，不能带入真实用户流程。

不优先引入：数据库、UI、引擎内 LLM、通用表达式执行器、并行调度、新插件层。先用现有文件结构完成简化。

- 保持 Python、Schema、JSON 文件存储、`engine/bin/aiwf` 入口和 Agent 驱动架构。
- 用小说场景作为已有实证；短剧、游戏和软件开发只做适用性推演，不声称已有对应案例验证。

## 8. 如何验证“确实更简单”

未来验证应保持相同业务目标和检查强度，不能靠删除验收、改恒真分支或吞掉错误让流程变短。

### 功能与可靠性验收

- 对象、数组、数字、布尔、文件引用跨父子流程传递保留类型。
- 相同引用在 inputs/items/when/依赖收集中的含义一致。
- 缺字段、分支未产出、首轮自引用等问题有定位明确的错误；静态不能证明的条件明确在运行前置检查。
- 只有一个 task 的流程能自然结束；内联循环无需空壳定稿节点。
- 章节返工不切换章号；进入下一章不误用上一章 previous_output。
- 质检拒绝包含原因且进入真实返工；达到本地上限会停止；人工验收不能被自动跨过。
- 改变上游条件会重新计算受影响分支；不同分支汇合后的缺失值不能静默使用旧值。
- 父子嵌套、失败恢复、换 Agent 接管后上报对象正确；旧动作结果被拒绝。
- 动态清单无新项时等待、明确 done 才结束；静态空清单可以结束。
- 产物按声明记录并可定位；重复运行不因复用同一目录的旧文件而错误计数或覆盖无关产物。

### 易用性指标

- 创建 Agent 只读对应 Skill 能否一次生成合法且可结束的定义。
- 完成同一案例所需的非业务 CLI 调用数，尤其空 complete 和父子切换次数。
- 需要手写的变量映射、图边、路由目标及仅用于协议适配的节点数。
- 定义期/运行期试错次数、修复一次错误所需读取的文档范围。
- 人只读流程定义，能否说明材料来源、产物去向、返工对象和终止条件。
- 换一个无上下文 Agent 能否仅凭任务包和产物索引继续完成。

本轮没有测量重设计后的成功率或节省比例，因此不承诺“提升多少百分比”。既有仿真可作为失败类型基线，不能把修复后的结果与不同目标的新案例直接做量化对比。
