## 0. 先回答三个疑问（每条都有实测）

### 疑问 1：视图命令怎么知道哪些 run 属于这个 plan？

答：靠 run 启动时自带的标识。实测可行：

```
$ aiwf run std.review-check -p subject=nothing -p criteria=none \
      -p plan=machine-core -p task=TASK-004
$ cat .aiwf/runs/std.review-check/<run>/record.json
inputs: {"subject":"nothing","criteria":"none","plan":"machine-core","task":"TASK-004"}
```

run 记录里确实留下了 `plan` / `task`（`inputs` 是自由 object，`-p` 不过滤、无 schema 约束）。

**但这恰好暴露了视图方案的内在矛盾**，见第 1 节。

### 疑问 2：怎么让用户看懂这个 plan？

**现在已经能看懂了——功劳全在 `index.md`，不在任何视图命令。**

实测 `machine-core/index.md` 的结构：

```
# 机器核心（控制台统一编排）
## 计划信息      游戏 / 计划 ID / 状态 / 目标 / 范围 / 创建·更新日期 / 稳定上下文
## 当前焦点      当前任务 / 当前状态 / 下一步 / 阻塞 / 必读文件 / 按需读取
## 任务          - [TASK-00N](tasks/…)｜描述｜状态：X｜依赖：Y   ×7
## 进度          已验收 3/7；进行中无；待验收 TASK-004；阻塞无；已取消或拆分无
```

**「目标 / 范围 / 焦点 / 下一步」这些是"看懂"的关键，而它们无法从 run 派生**——它们是人的意图，只能显式写。

视图命令若只 join 状态，输出要么丢掉这些（等于没看懂），要么把它们原样搬出来（等于 `cat`）。所以视图命令对"看懂"这件事**几乎不贡献**。

### 疑问 3：怎么看到还有哪些任务要继续做？

可以算：任务行 −（已完成 / 已取消）。**但前提是状态准**，而 8 态里只有 4–5 个能从 run 派生，3–4 个（待开始 / 阻塞 / 已拆分 / 已取消）必须人工写。

而实测已经证明**人工写的状态会漂**（`plan_in_engine_20261004.md` §1.3）：`visual-polish/index.md:45` 出现了 8 态之外的 `已验收`。

## 1. 视图方案的内在矛盾（本轮的核心发现）

视图要工作，依赖这条链：

```
视图命令 → 扫 runs → 按 inputs.plan 分组 → join index.md 的任务行
```

要让它跑起来，**每个 run 启动时就必须已经知道自己是哪个 plan 的哪个 task**：

```
aiwf run <workflow> -p plan=machine-core -p task=TASK-004
                       ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^  这个值从哪来？
```

这个值只有一个来源——**plan 本身**（任务清单里写着"TASK-004 属于 machine-core"）。

于是：

> **plan 必须先于 run 存在（run 要引用它），那它就不可能是 run 的派生物。**
> **视图方案把 plan 定义为 run 的视图，方向是反的。**

这不是实现问题，是**语义方向问题**。而且它带来一个实操脆弱点：既然标识靠命令行手传，**忘了传 / 传错，这个 run 就永远和 plan 脱钩**，视图看不见它，且事后无法补。一个需要"每次记得做对"的关联，不能作为长线跟踪的基础。

**所以：plan 是源（source of truth），run 是 plan 的一种执行手段。** 你的直觉成立。

---

## 2. 关系模型：plan : run = 1 : N

| 关系 | 说明 |
|---|---|
| 一个 plan 有 N 个 task | `machine-core` = 7 个 task |
| 一个 task 有 0..N 个 run | 未开始 = 0；返工（`revise`）= 多个（每次 revise 是新 activation） |
| 一个 run 对应一个 workflow | 同一 plan 的不同 task 可用不同骨架（写 spec / 改代码 / 回归） |

实测确认一个 task 可以有多次 activation（`record.json` 的 `activation_id` / `revision` 字段）。

**task id 跨 plan 重复**（实测：`machine-core` 是 TASK-001~007，`power` 是 TASK-001~012）→ **关联键必须是 `(plan, task)` 组合，单靠 `task` 会串。**

## 3. 独立机制的形态：三层分工

"独立"不等于"再起一个存储"。真正要做的是**把职责切开**：

| 层 | 谁负责 | 承载什么 |
|---|---|---|
| **清单** | 源 | 有哪些 task、依赖、目标、范围 |
| **计划态**（规划期） | AI 写 | 待开始 / 阻塞 / 已拆分 / 已取消 / 焦点 |
| **执行态** | 引擎派生 | 进行中 / 待验收 / 已完成 / 验收未通过（从 run 事实算，不手写） |
| **视图** | 生成 | 给人看的 `index.md`：一眼看出焦点、任务、进度 |

关键判断：**执行态必须从 run 派生，规划态必须人工写，两者在同一份文档里并存**——现状正是这两者混在一个 `｜状态：X｜` 字段里、由两个散文 skill 各写一半、且都无枚举校验，才漂的。

## 4. 清单存哪：两种源（这是本轮真正的选项分歧）

| | **M1 Markdown 为源** | **M2 JSON 为源** |
|---|---|---|
| 清单承载 | `plan/<id>/index.md`（现状，格式已 106/106 统一） | `.aiwf/plans/<id>/plan.json` |
| 人可读可编辑 | ✅ 直接改 markdown | ❌ 改 JSON，或看生成的 md |
| 依赖表达 | 自由，支持区间写法 `TASK-003～007`（实测存在） | 需标准化为数组，失去人类便利语法 |
| 机器校验 | 需解析（格式已统一，可行） | 天然 |
| `index.md` 角色 | 源 | 生成物 |
| 迁移成本 | **0**（源已存在） | 106 个 task 要迁移 / 写转换器 |
| 与 inbox 范式 | 一致（*Markdown is the source of truth*） | 相反 |
| 与"一眼看懂" | 天然 | 需额外渲染 |

实测支持 M1 的证据：**15 个 plan、106 个任务行、严格四段格式、零例外**（`plan_in_engine_20261004.md` §1.2）。源已经在，而且质量高。

## 5. 决策 12 候选

| 选项 | 清单 | aiwf 提供 | 代价 |
|---|---|---|---|
| **A 纯视图**（上一轮） | 留 `index.md` | 只 join 状态 | **已被第 1 节否掉**（方向反） |
| **B（推荐）Markdown 为源 + 机器能力** | 留 `index.md`，但**必须过校验** | `plan list / show / check / status / focus / run` | 需写解析 + 校验；g-plan 增加一步 `plan check` |
| **C 清单进 aiwf** | `.aiwf/plans/*.json` | 全量：增删改任务 + 状态 + 视图 | 106 task 迁移；`index.md` 变生成物；失去自由语法 |

**推荐 B。**

判据：
1. **它对准根因**——现状漂移的原因是"缺枚举约束、缺依赖校验"，不是"缺存储"。B 直接把校验补上：`plan check` 能立刻报出那 1 处 `已验收`、能查悬空依赖与环。
2. **零迁移**——源已是统一格式，解析即可，不动 106 个任务。
3. **不切断"人可读"**——plan 的核心价值是"一眼看懂"，markdown 是它的自然载体；C 会把源变成 JSON，视图要靠生成，反而增加一层。
4. **与两个既有先例一致**——`inbox`（markdown 为源 + thin layer 做机器的事）、`wf index`（生成产物）。

B 追加的一条硬约定：**g-plan 写完 `index.md` 必须跑 `plan check`**。这把"格式统一"从**碰巧**变成**保证**——这是 B 相对现状唯一的实操新增。

## 6. B 的具体形状（供判断粒度，非已定设计）

| 命令 | 做什么 | 读/写 |
|---|---|---|
| `plan list` | 列所有 plan：id / 状态 / 进度（task 计数） | 只读 |
| `plan show <id>` | 一个 plan 的清单 + 状态（执行态用 run 覆盖） | 只读 |
| `plan check [<id>]` | 校验：状态枚举 / 依赖存在且无环 / 格式完整 / 文档状态 vs run 派生是否一致 | 只读 |
| `plan status` | 用 run 事实派生执行态，与文档对比（只报不改） | 只读 |
| `plan focus <plan>[/<task>]` | 写「当前焦点」（显式，不可派生） | 写 index.md |
| `plan run <plan>/<task> [workflow]` | 启动 run，**自动带 `-p plan=… -p task=…`**，结束后派生状态 | 启动 run |
| `plan sync`（可选） | 把派生出的执行态原地回填 `｜状态：X｜` | 写 index.md |

注意 `plan run` 是**唯一消除"手传标识"的出口**——它同时解决了疑问 1 的脆弱点：标识由命令注入，不靠人记。

**与 aiwf run 的关系**：`plan run` 是 `run` 的一层薄包装，不新增引擎能力；run 记录格式不变（`inputs.plan`/`inputs.task` 是已实测可行的自由字段）。

## 7bis. 第一批实施记录（只读核心）

已落地并实测，`plan` 的位置与 `inbox` 一致：`<root>/plans/<plan-id>/index.md`。

| 命令 | 行为 |
|---|---|
| `plan list` | 全部计划：状态 / 完成数 / 焦点 / 名称；`--json` |
| `plan show <id>` | 目标、范围、焦点、任务、待办；`--no-runs` 关闭 run 派生 |
| `plan status` | 用 run 事实派生执行态，与文档并排，不一致标 `drift` |
| `plan check [<id>]` | 校验词表 / 依赖存在与成环 / 目标范围必填 / 焦点 / 进度一致 |
| `plan path` | 打印目录与各计划入口；`--dir PATH` 可指向别处 |

**实测（godot_agent 真实数据：15 个 plan / 106 个任务，跨 3 个游戏）**：`check` 报出
**6 处真实缺陷，零误报**——`visual-polish` 的状态越界（`已验收`，2 处同源）＋
`demo-extend` / `playable-demo` 缺必填的「目标」「范围」。

**实测中修正的三处过度严格**（都是我的判定错，不是数据错）：

1. 任务行可有第 5 段（`｜并入计划 machine-core`）—— 依赖须按单段解析，多出部分记备注；
2. 任务行可无链接（`- TASK-008｜…`，迁移件）—— 初版漏读 5 个任务并误报未知依赖；
3. 进度分母口径仓库内不统一（`demo01` 用活跃数 10/10，`power` 用总数 10/12），
   且行内可有跨计划引用（`TASK-002→demo01 TASK-009`）→ 改为只校验分子、
   且只比较属于本计划的 id。

空目录视为健康（对齐 inbox「缺失文件是空文档，不是错误」）。
