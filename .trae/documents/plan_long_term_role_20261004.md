## 0. 本轮问题

主人指出 plan 的两个真实作用，并问它们在 aiwf 上表现如何：

1. **长线任务跟踪** —— 几天甚至更久；一眼看出当前长线任务是哪个、进展到哪一步，不迷失方向与进度。
2. **整体回顾** —— 除当前 plan 外，还有哪些 plan 做过、哪些在进行。

我上一轮把 plan 当成"任务状态的容器"来讨论，**漏掉了这两个作用**。而它们才是 plan 存在的理由。

## 1. 更正：状态是 AI 维护的，漂移另有其因

### 1.1 事实更正

> 主人澄清：`plan/<plan-id>/index.md` **不是人维护的，是 AI 通过 `g-plan` skill 维护的**（执行态由 `g-do` 维护）。

我上一轮写成"人手维护会烂"，**归因错误**，此处更正。

### 1.2 那为什么会漂？因为写入方是两个散文 skill

`g-do/SKILL.md:143` 明写分工：

> 状态唯一权威在 `g-do` 的「状态流转」。本技能（`g-plan`）只写 `待开始`（创建任务时）、`已拆分`、`已取消`，不推进任何执行态（进行中 / 待验收 / 已完成 / 验收未通过 / 阻塞）。

也就是说**同一个 `｜状态：X｜` 字段由两个 skill 协同写**，而两个都是散文、**没有任何机器校验**。于是 `已验收` 这种不在 8 态枚举里的词就落进来了（`visual-polish/index.md:45`）。

**写入方是 AI 也照样漂。** 根因不是"谁不认真"，是**缺枚举约束**。

### 1.3 更强的发现：plan 级状态连枚举都没有

`index.md` 里还有一个 plan 自己的状态（`计划信息 · 状态`）。实测 `mc-plus` 的 12 个 plan：

| plan | 计划状态 |
|---|---|
| arch-mod | 执行中 |
| hinge-usability / machine-core / work-config-panels | 规划中 |
| demo01 / operate-ext / polish-01 / power / powered-axle / sequencer-mechanical-loop / visual-polish | 已完成 |
| demo02 | 已取消 |

**4 种值，全仓没有任何一处定义它们的全集或转换规则。** g-do 的 8 态是 *task* 级；g-plan 只在「计划收口」里提了"标为 `已完成`"。

**而且已经滞后**：`machine-core` 写"规划中"，但它 7 个 TASK 里已有 3 个已完成、TASK-004 待验收 —— 实际早已在执行。

这一条比 §1.2 更值得注意：**task 状态至少有 8 态枚举可校验，plan 状态连枚举都没有，且没有明确的维护者**（g-do 说"不推进执行态"，g-plan 只写规划态，两边都不认领它）。

## 2. 两个作用分别需要什么

| 作用 | 需要的东西 | 性质 |
|---|---|---|
| ① 长线跟踪 | (a) **焦点锚**："当前长线任务是哪个" | 状态，跨会话持久 |
| | (b) **进展**："到哪一步" | 派生 |
| | (c) 随时可查（AI 每次醒来都要读） | 存储 |
| ② 整体回顾 | (d) 全部 plan 的清单 + 状态 | 聚合视图 |

**(a) 是 Godot 现状唯一显式存储的东西** —— `project/.active-project`：

```
project: mc-plus
stage: plan
plan: machine-core
```

另有每游戏一份 `.project-focus`（切换项目时记忆上次 stage/plan）。`manage_project.py current` / `list` 就是读它。

**(d) 反而没有工具**：`mc-plus` 下没有任何 plan 汇总文件（实测只有 `design/index.md` 与 `README.md`）。要"整体回顾"只能 `ls plan/` 再逐个 `cat index.md`。**这是 Godot 现状也缺的。**

## 3. aiwf 现状：零支撑 —— 不是缺功能，是缺一层

### 3.1 层次对照

```
godot_agent        repo ──→ game ──→ plan ──→ task
aiwf                root ──→ workflow ──→ run
```

对应关系（"一项目 = 一游戏"下）：

| Godot | aiwf | 状态 |
|---|---|---|
| `game`（一个游戏项目） | `root`（一个 `.aiwf/` 目录） | ✅ 决策 10 已定 |
| `task`（一次实施） | `run`（一次 workflow 执行） | ✅ 决策 10 已定 |
| **`plan`（一个里程碑）** | **（空）** | ❌ **没有对应物** |

**主人问的两个作用，全部落在这一层上。** 所以答案不是"aiwf 做得不好"，而是"aiwf 里没有这一层"。

### 3.2 最接近的是 `runs list`，但它是技术视图

实测输出（`%TEMP%/aiwf-pro-1`）：

```
2026-10-04T15:37:24  20261004-153724-1e3b09  parent-probe     running  None ms  0 nodes
2026-10-04T15:26:45  20261004-152645-5fe471  std.review-loop  running  None ms  1 nodes
```

按 `workflow_id` + 状态 + 耗时组织。它能回答"执行过哪些 workflow"，**回答不了**"我的长线任务是哪个、做到哪了"。前者是执行视图，后者是工作视图。

## 4. 为什么不能让一个 run 充当 plan（关键取舍）

看上去有条省事的路：**run 生命周期本来就长** —— `awaiting_review` 是落盘的，可以挂几天等验收。那**一个 plan = 一个 run**，焦点与进展就直接是 run 的当前状态，不必新增任何概念。

两个硬伤：

**硬伤一：run 的定义在启动时冻结，而 plan 明确支持演进。**
1.1 的 run 启动时写定义快照，执行期**不能加节点**。而 `g-plan/SKILL.md:124-139` 有整节「执行期计划修复」——允许追加任务、修正依赖；实测数据里也有 3 个 `已拆分` 任务。**冻结的 run 表达不了演进的 plan。**

**硬伤二：一个 run 只跑一个 workflow，而 plan 里的 TASK 是异构的。**
`machine-core` 的 7 个 TASK 从"写 spec"到"移除时序器方块"到"整体回归"，理想上该用不同 workflow 骨架。一个 run 只能装一个。

结论：**plan : run = 1 : N，且这 N 个 run 可以用不同 workflow。** 这也是为什么 aiwf 里必须补出 plan 这一层，而不是把 run 改大。

## 5. 但那条派生链是完整的

```
run（事实：引擎落盘、不可变、有 journal 与定义快照）
  └→ task 执行态    5/8 可派生（进行中 / 待验收 / 已完成 / 验收未通过）
        └→ task 规划态    3/8 人工（待开始 / 阻塞 / 已拆分 / 已取消）
              └→ plan 状态    聚合，可派生
```

plan 状态的派生判据（草案）：

| 条件 | plan 状态 |
|---|---|
| 存在 task 处于 进行中 / 待验收 / 验收未通过 | 执行中 |
| 全部 task ∈ {已完成, 已取消}，且至少一个已完成 | 已完成 |
| 全部 task = 已取消 | 已取消 |
| 无任何 task 进入执行态 | 规划中 |

按这套判据，§1.3 那张表里 **12 个 plan 的状态全部可算出来**，且不会像 `machine-core` 那样滞后。

## 6. aiwf 相对现状的潜在优势（连同代价）

优势：

- run 记录**不可变 + 有 journal + 有定义快照** —— 比"AI 手写一个状态词"可信得多；
- review gate 是**引擎强制**的（`awaiting_review` + `verdict`），不靠散文纪律；
- 派生意味着**焦点与进展不会滞后**（§1.3 的两处滞后都能消除）。

代价：

- 要建立 run ↔ plan/task 的关联。走 `inputs.plan` / `inputs.task`（零 schema 改动 —— 实测 `inputs` 是自由 object 且落盘），但**靠约定**，漏传则该 run 成孤儿。

## 7. 待拍板：决策 11（重述，判据已更新）

**plan 这一层在 aiwf 里由什么承载。**

| 选项 | 内容 | ① 长线跟踪 | ② 整体回顾 | 代价 |
|---|---|---|---|---|
| **A 视图命令** | `plan list` / `plan status` / `plan check`，只读；plan 仍是文档 | 半（只有进展，无焦点） | ✅ | 焦点仍靠人/agent 记；零风险 |
| **B（推荐）A + 显式焦点** | 加 `plan focus` —— 读写一个焦点，对应 `.active-project` 的 plan 层 | ✅ | ✅ | 多一个状态文件要维护 |
| C plan 定义进引擎 | task 列表搬进 `.aiwf/plans/*.json` | ✅ | ✅ | 双写或取代文档；被"不提前造机制"否（定义已在 106/106 统一的文档里） |

推荐 **B**，判据：

- 诉求① 的核心是「**当前长线任务是哪个**」，这是**一个焦点**，不能可靠派生 —— "最近有活动的那条" ≠ "当前焦点"（收口后的 plan 仍会是最新的那条）；而 Godot 现状本来就是**显式存**的（`.active-project`）。
- 诉求② 由 `plan list` 直接满足，而这连 Godot 现状都没有，属净增。
- A 只能答②、答不了①，等于把主人最看重的那半留着。

决策 11 定了，第二项是**焦点由谁写**（人 / agent 显式调 `plan focus`，还是 `plan run` 时自动跟随）。

## 8. 一个待澄清（不占本次拍板）

"一项目 = 一游戏"后，`.active-project` 的 `project:` 层消失（一个 `.aiwf/` 就是一个游戏），但 **`stage:`（design / spec / plan）这一层怎么办** —— 它在 aiwf 里同样没有对应物，而它决定"现在该做什么类型的工作"。焦点 = `stage` + `plan` 还是只剩下 `plan`，需要单独定。
