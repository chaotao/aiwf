# 收件箱：记下不阻塞当前流程的想法与问题

项目开发中途冒出的点子、体验问题、技术债，不该打断当前任务，也不该被随手丢掉。
把它们记进项目的收件箱，之后再整理交接。

收件箱在 `<AIWF_HOME>/inbox/`，与 `runs/` 并列，**跨运行、跨计划存活**。
它不是任务列表：不排期、不设负责人、不跟踪条目是否做完，也不属于任何 run 的状态。

## 何时记

- 用户说「先记下」「不挡这一轮」「以后再说」「记到 inbox」。
- 执行任务途中发现与本节点无关的问题或想法。
- 一个想法确定不进本轮流程，但值得留档。

## 何时不记（硬约束）

- **当前节点的产物缺陷**：该走 `check` 的 REVISE、`aiwf fail` 或 `aiwf revise`。
  把验收问题记进收件箱就算绕过质检 —— 不许这么做。
- 现在就要做的事：走创建流程或直接做完，不要先记一条。
- 一次性的短任务：记下来比直接做完更慢。

拿不准时问一句：记进收件箱，还是改当前任务 / 留给后续节点。
**不得把当前验收问题偷偷扔掉。**

## 记下

```bash
aiwf inbox add "四种砖是否需要材料玩法差异" --why 用户明确不挡 --type 想法
```

- `--why` **必填**，只能取四值（可并列，用 `/` 分隔）：
  `非本节点` / `非本流程后续节点` / `用户明确不挡` / `范围收缩`。
  它是被强制回答的「为什么这件事可以等」。缺了就停下问，不要硬记。
- `--type` 取 `想法` / `体验` / `问题` / `技术债`，只是标签，不驱动分流。
- 来源：在 run 中记就带 `--run <根run_id> --node <节点id>`；否则用 `--source` 或省略。
  这两项**只记录、不校验**，不读写运行记录。
- 内容过多用 `--note-file <path>`，或写 `notes/INB-NNN.md` 后在条目里链接。
  整条正文控制在 500 字以内，写清目标、现状与边界。

**先归类再新开**：新想法先扫 `aiwf inbox list`，能并进已有条目的就并入，
不要为同类事项反复开新号：

```bash
aiwf inbox add "补充：砖的材质还影响音效" --why 用户明确不挡 --merge-into INB-001
```

编号 `INB-NNN` 由活页与历史共用、稳定递增、不复用，`拆自` / `吸收` / `相关` 才指得住。

## 列出与查看

```bash
aiwf inbox list                  # 只读活页索引，只展开未处理
aiwf inbox list --all            # 追加显示已归档条目
aiwf inbox list --run <run_id>   # 只看某个 run 记下的
aiwf inbox show INB-006          # 单条全文
```

默认**不读历史正文**；`--all` 也只补标题行。不要为了列出去通读 `history.md`。

## 消化（用户要求整理，或流程收口时）

1. `aiwf inbox list` 看未处理条目，**按去向**分组建议，不按类型分组：
   纳入当前流程 / 留给下一轮 / 交给别的计划或文档 / 丢弃。
2. 等用户选定后再改状态。**本能力只交接，不代做**：不写策划、不拆任务、不改当前 run 状态。
3. 交接成功用 `已交接`，明确不做用 `丢弃`，并写去向（`去向` 只写交给谁，**不写「已完成」**）：

```bash
aiwf inbox resolve INB-006 --status 已交接 --to "纳入 next-round"
aiwf inbox resolve INB-002 --status 丢弃 --to "与既有方案重复"
```

`resolve` 一步完成改状态、追加历史、从活页删除，不会留下半归档状态。
去掉 `--why` 的理由行是刻意的：条目一旦交接，停放理由就失去意义。

## 重组（拆分 / 合并）

拆分由人来判断，**引擎不代写新条目正文**：`--split-into` 只记录去向，
新条目另行 `add --split-from` 产生。

```bash
aiwf inbox resolve INB-001 --to "留给下一轮" --split-into INB-007,INB-008
aiwf inbox add "缓存失效的具体复现步骤" --why 非本节点 --split-from INB-001
```

合并用 `add --merge-into`（见上），活页里同类事项只留一条。

## 校验

```bash
aiwf inbox check        # rc=0 干净；有问题打印清单并 rc=2
```

检查：未处理条目的必填字段、索引与条目集合是否一致、编号是否重复、
历史条目是否都有去向、活页里是否残留已处理状态。
`aiwf inbox path` 打印目录，便于直接打开文件。

## 格式

```text
<AIWF_HOME>/inbox/
  inbox.md           # 活页，仅未处理条目；文首是索引
  history.md         # 已交接 / 丢弃；首次归档时创建，只追加不重排
  notes/INB-NNN.md   # 可选，单条内容过多时的详情
```

字段：`状态`（活页仅 `未处理`）、`类型`、`日期`（自动填）、`来源`、`摘要`、
`为何停放`（未处理必填）、`拆自` / `吸收` / `相关` / `备注`（可选）、
`去向`（仅历史）。

目录纳入版本管理（与 `.aiwf/runs/` 一致）：停放的条目是项目记忆，不要删。

## 与运行的关系

- 记录**不产生 node_run、不消耗 check 预算、不改 run 状态**；记完照常继续当前节点。
- 引擎**不会**把收件箱条目自动喂进任何运行。要用某条，由用户或你在启动下一轮时
  显式作为入参传入（`-p` / `--input-file`），或写进项目 `config.json` 的 `run_defaults`。
- 唯一红线仍是上面「何时不记」第一条：当前节点的缺陷不在这里处理。
