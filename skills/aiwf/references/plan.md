# 计划：长线任务的全局视角

一个 run 只说明**一次执行**发生了什么。跨天、跨周的项目还需要另一层：
有哪些计划、当前焦点是哪个、还剩哪些任务。这一层就是 plan。

计划在 `<AIWF_HOME>/plans/<plan-id>/`（默认就是 `<项目>/.aiwf/plans/<plan-id>/`），
与 `runs/`、`inbox/` 并列，**跨 run 存活**。
run 答「发生了什么」，计划答「我在做什么、做到哪一步」。

## 何时用

- 要开一个跨多次实施的项目：先有目标和范围，再有任务。
- 想知道**当前该做什么**、还剩哪些任务 —— 而不是某个 run 跑到哪了。
- 想一次看全：哪些计划在做、哪些已收口。
- 接手上次会话或别人留下的项目，先看有哪些计划与焦点。

一次性短任务不需要计划，直接做完。

## 命令

```bash
# 读
aiwf plan list                        # 全部计划：状态、完成数、焦点
aiwf plan list --json
aiwf plan show machine-core           # 目标 / 范围 / 焦点 / 任务 / 待办
aiwf plan show machine-core --no-runs # 不读运行记录，只看文档
aiwf plan status                      # 用 run 事实派生执行态，与文档并排
aiwf plan check                       # 校验状态词表与依赖图
aiwf plan path                        # 打印计划目录

# 写
aiwf plan new machine-core --goal "…" --scope "…"     # 建空计划
aiwf plan task add machine-core TASK-005 --name "…" --deps TASK-003,TASK-004
aiwf plan task add machine-core TASK-006 --name "…" --deps TASK-003～005
aiwf plan focus machine-core TASK-005                 # 挪焦点；none 清空
aiwf plan sync machine-core                           # 干跑：把 run 事实折回文档
aiwf plan sync machine-core --write                   # 真的落盘
aiwf plan sync machine-core --write --renumber        # 顺带把分母改成任务数
```

`--dir <PATH>` 可指向别处的计划目录（从旧结构渐进迁移时有用）。

## 与运行的关系

- **计划不是 run 的视图，而是它的来源。** run 启动时用
  `-p plan=<id> -p task=<TASK-NNN>` 带上身份，计划才认得它 —— 先有计划，才有这次运行。
- 关联键是 `(plan, task)`：`TASK-NNN` 只在**本计划内**唯一，编号在不同计划间重复。
- `plan status` 由此派生执行态（进行中 / 待验收 / 已完成 / 验收未通过），
  与文档里的值并排显示，不一致时标 `drift`。
- 规划态（待开始 / 已拆分 / 已取消）没有 run 可读，只能写。

## 状态词表

任务状态（权威在 `g-do` 的状态流转，8 个）：
`待开始` / `进行中` / `待验收` / `已完成` / `验收未通过` / `阻塞` / `已拆分` / `已取消`。

计划状态：
`规划中` / `执行中` / `待整体验收` / `已完成` / `已暂停` / `已取消`。
（`已取消` 是实测在用、但上游格式文档尚未收录的值。）

`plan check` 拒绝词表外的状态 —— 这类漂移正是建立本层的原因：
同一个 `状态：` 字段曾被两个散文 skill 各写一半，结果出现了词表外的 `已验收`。

## 校验什么

```bash
aiwf plan check            # rc=0 干净；有问题打印清单并 rc=2
```

- 任务级与计划级状态是否在词表内；
- 依赖是否存在、是否成环；
- 计划信息是否含「目标」和「范围」（缺任一项不算计划已建成）；
- 焦点是否指向一个真实任务；
- 「进度」块是否与任务列表一致（已完成数 + 各状态的 id 集合）。

已建成的计划目录为空时视为健康，不算错误。

## 格式

```text
<AIWF_HOME>/plans/<plan-id>/        # 默认即 <项目>/.aiwf/plans/<plan-id>/
  index.md            # 唯一事实来源：目标、范围、焦点、任务、进度
  context.md          # 可选：跨任务稳定的上下文
  tasks/TASK-NNN.md   # 可选：单任务契约
```

`index.md` 的四个小节被本层解析：

```markdown
# 计划名称
## 计划信息   目标 / 范围 / 状态 / 游戏 / 计划 ID / 创建·更新日期
## 当前焦点   当前任务 / 当前状态 / 下一步 / 阻塞 / 必读文件
## 任务       - [TASK-001](tasks/TASK-001.md)｜名称｜状态：待开始｜依赖：无
## 进度       已验收：0 / 2
```

解析容错（都来自真实文件）：

- 任务行可省链接：`- TASK-008｜名称｜状态：已完成｜依赖：无`；
- 依赖后可再有 `｜` 段，如「并入计划 `machine-core`」，它记作备注，不算依赖；
- 依赖支持区间简写：`TASK-003～007`；
- 「进度」行可带括注与跨计划引用，如 `TASK-002→demo01 TASK-009`；
  只比较属于本计划的 id，且**只校验分子**（分母口径各计划自定，有 10/10 也有 10/12）。

## 写的时候只动一行

计划是**人写的**文件，所以写命令是外科手术而非重新排版：只替换必须改的那一
行，其余字节（散文、备注、必读文件清单、空行）原样保留。
`plan sync` 默认**干跑**，只打印将要改的行；加 `--write` 才落盘。

`sync` 只回写 run 真正掌握的事实：

- 任务行的 `状态：`，且只覆盖「待开始 / 进行中 / 待验收 / 已完成 / 验收未通过 /
  阻塞」——`已取消` / `已拆分` 是人的规划决定，旧 run 不能让它复活；
- 「当前焦点」的 `当前状态：`，**仅当它是纯状态词**（`待开始`）时才跟随；
- `进度` 块里**已经存在**的标签行，且只在该行的 id 集合确实不对时才改。
  行上人的注解原样保留：`TASK-002→demo01 TASK-009`、`（并入 machine-core）`
  不会被"重新列举"抹掉。也不会凭空新增一行。

`已验收` 行只改 `N / M` 这一截；后面的括注（`（TASK-001～008）`）是作者的话，
原样留着。分母是各计划自定的口径（有 `10 / 10` 也有 `10 / 12`），`sync` 默认
保留原分母，必要时用 `--renumber` 把它重置为任务总数。

它**不动**带注解的焦点行——`待验收（手动实机验收）` 里那句括注是作者的解释，
只换状态词就变成假话。要挪焦点用 `plan focus`。

于是有个可预期的不对称：`plan check` 会指出这个词表外/对不上的地方，而
`sync` 只修它**有 run 事实可依据**的部分。剩下的（比如手写的 `已验收`）要人自己拍。

`plan task add` 写入前先校验：id 未被占用、依赖都存在、状态在词表内，
还支持 `TASK-003～005` 区间简写。

目录纳入版本管理（与 `.aiwf/runs/`、`.aiwf/inbox/` 一致）：计划是项目记忆。
在仓库里就是 `.aiwf/plans/`（`AIWF_HOME` 未改时）。
